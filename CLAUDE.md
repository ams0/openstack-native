# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Deployment configuration (no application source code) for running the **OpenStack control plane on vanilla Kubernetes**, using the **upstream `openstack-helm` charts** pulled directly from `https://opendev.org/openstack/openstack-helm` — this repo only provides values files, infrastructure CRs, and ArgoCD Applications. Compute nodes (nova-compute, neutron L2 agents, libvirt) run on **bare metal outside the cluster**; only APIs, schedulers, conductors, and infra (MariaDB / RabbitMQ / Memcached) run in Kubernetes.

Everything is YAML + Bash + Make. There is no build, no compiler, no unit test suite.

## Commands

```bash
make help                    # lists every target (default goal)
make check-tools             # verify kind, kubectl, helm

make cluster-up              # kind cluster "openstack-cluster" from kind-cluster.yaml
make install-operators       # cert-manager, MariaDB (CRDs then operator), RabbitMQ cluster +
                             #   topology operators, CloudNativePG, External Secrets
make setup-secrets           # generate random passwords → k8s Secrets (+ sealed secrets if kubeseal)
make deploy-infrastructure   # memcached chart, MariaDB CR + Databases, RabbitMQ certs/cluster/users
make deploy-all              # cluster-up → install-operators → setup-secrets → deploy-infrastructure

make install-argocd          # ArgoCD + print initial admin password
make generate-values         # patch the ArgoCD keystone Application with live cluster passwords
make deploy-services-gitops  # apply gitops/app-of-apps.yaml

make install-lb              # cloud-provider-kind (host daemon) — gives kind type=LoadBalancer
make install-csi             # csi-driver-host-path + snapshot-controller + csi-hostpath-sc
make test-lb / test-storage  # verify those two actually work (real provisioning/traffic)

make load-openstack-images   # side-load amd64 OpenStack images (REQUIRED on Apple Silicon)
make deploy-openstack        # keystone → placement → glance → neutron → nova → horizon
make test-openstack          # real token + catalog + Horizon login, not just pod status

make test                    # test-infrastructure + test-services (readiness checks only)
make test-api                # scripts/test-services.sh — real API calls, needs port-forwards
make show-status / show-credentials / logs-infrastructure / logs-services / logs-keystone
make port-forward            # keystone 5000, glance 9292, placement 8778, horizon 8080
make argocd-port-forward     # ArgoCD UI on 8080

make clean                   # services → infrastructure → operators → argocd → cluster-down
```

Overrides: `CLUSTER_NAME`, `NAMESPACE` (default `openstack`), `ARGOCD_NAMESPACE`, `KIND_CONFIG`, `KUBECONTEXT`, `TIMEOUT`.

Linting is Helm-only: `helm lint charts/<name>` and `helm template <rel> charts/<name>` (what CI runs).

## Two deployment paths — know which one you are touching

1. **Imperative** (`make deploy-*`): plain `kubectl apply` / `helm upgrade --install` against the local files. Uses `clusters/mariadb-direct.yaml` — a *raw* MariaDB CR plus the per-service `Database` objects (keystone, glance, placement, neutron, nova, nova-api, nova-cell0).
2. **GitOps** (`gitops/app-of-apps.yaml`): ArgoCD recurses `gitops/`, ordered by `argocd.argoproj.io/sync-wave` — `-1` external-secrets, `0` operators + namespace, `1` MariaDB/RabbitMQ clusters, `10` OpenStack services. Here `clusters/mariadb-cluster.yaml` is an ArgoCD **Application** (mariadb-operator's `mariadb-cluster` chart), *not* a CR.

Same-named files in `clusters/` therefore mean different things depending on path. `mariadb-direct.yaml` exists precisely because the ArgoCD manifest cannot be `kubectl apply`-ed without ArgoCD.

**GitOps reads from GitHub, not from your working tree.** `gitops/*` and the keystone multi-source Application hardcode `repoURL: https://github.com/ams0/openstack-native`, `targetRevision: main`. Edits to `values/` or `clusters/` have no effect on an ArgoCD-managed cluster until they are committed and pushed to `main`. For local iteration, use the imperative path or `helm upgrade` with the local values file.

## Secrets flow

Passwords are generated by operators/scripts at deploy time and never live in git:

- `values/*.yaml` carry literal placeholders — `REPLACE_WITH_MARIADB_ROOT_PASSWORD`, `REPLACE_WITH_RABBITMQ_ADMIN_PASSWORD`, `REPLACE_WITH_RABBITMQ_KEYSTONE_PASSWORD` (older files use `PASSWORD_PLACEHOLDER`). Keep them as placeholders when editing.
- `scripts/setup-secrets.sh` creates `mariadb-basic-root`, `openstack-rabbitmq-default-user`, `rabbitmq-keystone-user` in the `openstack` namespace (and sealed variants if `kubeseal` + controller are present).
- `make generate-values` injects the live passwords as ArgoCD Helm `parameters` on the keystone Application — the values file in git stays clean. This must be re-run after any keystone Application re-sync that resets `spec.sources`.
- `scripts/update-values-with-secrets.sh` / `update-passwords*.sh` do the same by `sed`-ing local values files; their output matches gitignored patterns (`values/*-generated.yaml`, `clusters/sealed-*.yaml`, `*-with-passwords.yaml`) — do not un-ignore those.

## Service wiring conventions (used across every values file)

| Dependency | Endpoint |
|---|---|
| MariaDB | `mariadb-basic:3306`, admin user `root`, per-service DB path (`/keystone`, `/nova`, …) |
| RabbitMQ | `openstack-rabbitmq:5671` **AMQPS/TLS**, CA/cert in `rabbitmq-tls-secret` / `openstack-ca-secret`, per-service vhost (`/keystone`) and per-service User+Permission CRs in `clusters/rabbitmq-users.yaml` |
| Memcached | `memcached-service:11211` (local chart `charts/memcached`) |

Adding a service means: a `Database` entry in `clusters/mariadb-direct.yaml`, a Vhost/User/Permission trio in `clusters/rabbitmq-users.yaml`, a `values/<svc>-values.yaml`, and a `gitops/2-Services/<svc>.yaml` Application following the keystone multi-source pattern (upstream chart + `$values` ref to this repo).

## Cluster add-ons (kind lab)

Stock kind has no LoadBalancer and no CSI driver — see `docs/KIND-ADDONS.md`. Two things to remember:

- **`cloud-provider-kind` is a host daemon, not a workload.** It must be running (`sudo cloud-provider-kind --enable-lb-port-mapping`) or every `type: LoadBalancer` Service sits `<pending>`. Nothing in `gitops/` or `make deploy-all` starts it. It watches all kind clusters, so it survives a cluster recreate without a restart.
- **`csi-hostpath-sc` is the default StorageClass** (`make install-csi` clears the default flag on kind's `standard`). It is a single-node dev driver whose data dies with the cluster — pin anything that must outlive it to a class explicitly.
- **Volume expansion is offline.** Patching a PVC resizes the PV, but the PVC stays at the old size with `FileSystemResizePending` until the consuming pod restarts.
- **`kind-cluster.yaml` deliberately does not map host ports 80/443/5672** — kind binds extraPortMappings on `0.0.0.0` and would block cloud-provider-kind from publishing LB Services on those ports. Only NodePorts 31000–31002 are mapped.

## Deploying the OpenStack services

`gitops/` only has an Application for keystone, and it reads values from GitHub `main` — so for local work the imperative path is `scripts/deploy-service.sh <svc>`, which pulls the upstream chart into `.openstack-helm/`, fills the `REPLACE_WITH_*` placeholders from live cluster secrets into a temp file (never the repo), and layers `values/overrides/kind-lab.yaml` on top. `make deploy-openstack` runs the whole set in dependency order.

- **`values/overrides/kind-lab.yaml` is not optional.** Without it the charts request a `general`/`default` StorageClass that does not exist, enable RabbitMQ TLS in a way that fails to render, and start neutron/nova agent daemonsets that cannot work on this node. Each override carries a comment saying what breaks without it.
- **Placeholders, not literals.** Every `values/*.yaml` must use `REPLACE_WITH_MARIADB_ROOT_PASSWORD`, `REPLACE_WITH_RABBITMQ_ADMIN_PASSWORD`, `REPLACE_WITH_RABBITMQ_KEYSTONE_PASSWORD`, `REPLACE_WITH_RABBITMQ_ADMIN_USERNAME`. These files previously held real credentials and a generated `default_user_<random>` name that went stale on every cluster rebuild.
- **Nova has three databases**: `oslo_db`, `oslo_db_cell0`, `oslo_db_cell1` (there is no `oslo_db_api` — overriding it is silently ignored). Miss one and `nova-db-init` fails against the chart-default host `mariadb`.
- Neutron picks up `values/neutron-values-controlplane.yaml` automatically (server only); `values/neutron-values.yaml` is the agents-included variant for real compute nodes.

## Apple Silicon

**Read `docs/APPLE-SILICON.md` before touching images or the node platform.** OpenStack-Helm images are amd64-only and there are no arm64 builds anywhere.

- **Never run the kind node as amd64.** The emulated amd64 kubelet cannot parse the arm64 kernel's `/proc/cpuinfo` and dies (`could not detect clock speed`). Emulation covers userspace only. `KIND_PLATFORM` in the Makefile exists for amd64 hosts; on an M-series Mac use `KIND_PLATFORM=` (native).
- Images are side-loaded by `scripts/load-amd64-image.sh`, which rewrites `config.architecture` to `arm64` so containerd's CRI stops filtering them out, then imports straight into the node. **Pods must never pull** — a real pull re-resolves the upstream manifest and fails again.
- Any newly referenced image must be side-loaded first, or it lands in `ImagePullBackOff`.
- Docker Desktop rewrites `settings-store.json` on shutdown, so edit resources only while it is **stopped** (`docker desktop stop`).

## Gotchas

- **Node labels.** All `values/*.yaml` set node selector `openstack-control-plane=enabled`. `kind-cluster.yaml` now applies that label to the control-plane node at creation time, so pods schedule on a `make cluster-up` cluster. Any node created another way (a plain `kind create cluster`, an added worker, a real cluster) still needs `kubectl label node <node> openstack-control-plane=enabled` — and compute values additionally want `openstack-compute-node=enabled`, which nothing applies automatically.
- **Make targets swallow failures.** Most steps end in `|| true`, `|| echo "…may already be installed"`, or `2>/dev/null`, and `kubectl wait` failures are downgraded to warnings. Green Make output is not evidence of success — confirm with `kubectl get`/`make show-status` before claiming a deployment worked.
- `kind-cluster.yaml` maps host ports 80, 443, 5672, and NodePorts 31000–31002; services exposed for outside access must use those.
- `tmp/` is gitignored scratch (experimental RabbitMQ RBAC, SOPS, helm-secret wrapper) — not part of any deployment path.
- The repo root holds ad-hoc status notes (`COMPUTE-NODE-STATUS.md`, `RABBITMQ-TLS-ENABLED.md`, `SKYLINE-DEPLOYED.md`, `PASSWORDS-RESTORED.md`) that are point-in-time records of past cluster state, not specifications; verify against the cluster before trusting them.

## CI

- `.github/workflows/ci.yaml` — kind cluster → `install-operators` → `deploy-infrastructure` → `setup-secrets` → `test-infrastructure`; plus `make help` syntax check and `helm lint charts/*`. Services (keystone and beyond) are **not** deployed in CI.
- `.github/workflows/kind-test.yaml` — lint/template both local charts, then install `charts/memcached` and `charts/secret-generator` into a kind cluster and verify.
